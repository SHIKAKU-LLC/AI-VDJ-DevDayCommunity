# Decisions APIによる参加者の出番の調整

OpenAI Decisions APIを、次に流す12秒の音楽・映像セットの選択に組み込む。
投稿内容の審査ではなく、同じ参加者の繰り返し採用を調整する用途で使う。
実API応答・本番配備は未確認。既定では外部への問い合わせを行わない。

## 参加者に見える挙動

- 対象は品質確認済みで音楽・映像が両方12秒の投稿。ブラウザで読み込みができた候補から選ぶ。
- 採用回数が少ない参加者を優先し、同数ならサーバーの投稿受付時刻・受付番号の順。同一時刻の投稿も番号で区別する。
- 直前と同じ参加者が先頭なら、再生可能な別の参加者の最も早い候補へ譲る。採用回数による優先順位は別の参加者同士でも保持する。
- A1 → A2 → B1 → C1 が全件準備済みなら A1 → B1 → C1 → A2。A2は削除しない。
- 1人だけの場合は連続採用する。未完成・読み込み中の投稿を待って演出を止めず、準備できれば次回の候補へ戻す。
- 音楽と映像は常に同じ投稿のセット。再生開始の確認まで採用数を増やさず、再送でも一度だけ数える。
- 既存ジョブは投稿の受付記録から時刻・番号を補って選択する。受付番号がない過去の投稿の同時刻内の順序はID順で安定化する。

## APIの担当と固定ルール

[`POST /v1/decisions`](https://developers.openai.com/api/docs/guides/decisions) にモデル `gpt-6-luna`、質問種別 `choice` を指定する。

| APIへ渡す事実 | 意味 |
| --- | --- |
| `head_adopted_count` | 投稿順で先頭の参加者の採用回数 |
| `next_adopted_count` | サーバーが見つけた次候補の参加者の採用回数 |
| `head_is_previous_participant` | 先頭が直前に採用した参加者か |
| `next_is_different_participant` | 次候補が先頭とは別の参加者か |

投稿文・画像・名前・参加者ID・投稿ID・ルームIDは送信しない。
返答は `PLAY_HEAD`（先頭を再生）か `DEFER_REPEAT`（先頭を残して別の人へ譲る）の2択。
モデルに任意の投稿IDや順位を生成させない。サーバーが先に固定ルールから候補を限定し、モデルの回答がそのルールに合う場合だけ採用する。
そのためAPIが不調でも、同じ投稿順・公平ルールを継続できる。

通常のFIFOには問い合わせを行わない。現在のセットの再生開始を記録した後や再生中のポーリングで、繰り返し採用を調整する候補があれば先行問い合わせする。
Durable Objectのロック外で実行し、投稿受付・ハートビート・次の予約は応答を待たない。
再生予約時に、最新の採用回数・直前の参加者・ブラウザで読込済みの候補を再確認する。

## 遅延・失敗・費用の上限

- 応答本文を含め800msで打ち切る。429/5xx、通信失敗、拒否、不正回答、ルールに合わない回答は固定ルールへ戻す。
- 次の予約までに回答が届かない場合も即座に固定ルールで決定する。遅い回答で予約済み・再生中のセットを変更しない。
- 回答が対象とした先頭・次候補・採用数・直前の参加者が変わった場合は使わない。
- 問い合わせ前にDurable Objectへ実行予定を記録。同じ保留対象の投稿につき最大1回、1ルーム最大100回、自動リトライなし。
- 途中で再起動した不明な要求も再送しない。新しい候補に古い回答を流用せず、固定ルールで続行する。
- 金額の予約は既存の音楽・映像生成予算と別。API利用料金は[公式ガイド](https://developers.openai.com/api/docs/guides/decisions#pricing-and-availability)と利用プロジェクトの上限を確認する。

## 設定と確認

1. 対象Workerの実行時Secretに `OPENAI_API_KEY` を登録する。キーをビルド変数・Git・画面に入れない。
2. 承認済みの検証環境でビルド変数 `VDJ_DECISIONS_ENABLED=true` を指定する。Workerの `DECISIONS_ENABLED` に反映される。既存の12秒版 `AUDIENCE_MODE=true` が前提。
3. 準備済みのA1・A2・B1・C1で再生を開始する。オーナー権限の `/api/rooms/<roomId>/playback` のGETで、`decisions.enabled`、`calls`、`status` と `selection` を確認する。
4. A1の再生後に `status: ready`、B1の予約時に `selection.source: decisions` / `action: DEFER_REPEAT` が得られるか確認する。`rules` は固定ルールで選んだことを表す。
5. 無効化する場合は `VDJ_DECISIONS_ENABLED=false` で再配備する。新規要求を止め、保存済み回答も使わない。

`selection` は直近の予約を示す。実際の採用は `played` と `counts` で確認する。
本変更ではクラウド設定変更・配備・実API課金は行っていない。

## ローカル検証

```sh
node --test tests/playback-decisions.test.mjs tests/audience-queue.test.mjs tests/cloudflare-generation.test.mjs tests/cloudflare-room-api.test.mjs tests/judge-scenes.test.mjs
```

Node.js 24を推奨。Node.js 22.12で検証する場合は `node --experimental-sqlite --test ...` とする。
合成データ・インメモリDB・APIモックで以下を確認する。

- 投稿受付順、同一時刻の番号、一巡、連続採用の回避、単独参加者の継続、保留した投稿の後続採用。
- 固定選択肢のリクエストと適用、個人データを含まない入力、不正応答・429/5xx・タイムアウト・古い回答の代替。
- API待ち中の投稿受付・ハートビート・再生予約、停止後の遅延応答、再起動・ポーリング時の重複防止。
- 既存の12秒の共有時計、プリセットの一巡、採用回数の一度だけの加算。

実APIの可用性・レイテンシ・料金・会場での実機再生は、このローカル検証に含まない。
